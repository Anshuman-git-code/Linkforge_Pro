Prerequisites & One-time Setup
Why do these before anything else?

These are the tools and credentials your local machine needs to talk to AWS and run deployment scripts. Without them, every command in this guide will fail instantly. These are done once per machine — never repeated per project.

1
Install AWS CLI and verify
aws --version
# Expected: aws-cli/2.x.x Python/3.x.x ...
What is AWS CLI and why do you need it?

AWS CLI (Command Line Interface) lets you control every AWS service from your terminal instead of clicking through the web console. Every aws cloudformation deploy, aws lambda create-function, and aws s3 sync command in this guide runs through it. Without CLI, you would have to do every step manually in a browser — slow, error-prone, impossible to automate or repeat. Download from aws.amazon.com/cli if not installed.

2
Configure AWS credentials
aws configure
# AWS Access Key ID: <your key>
# AWS Secret Access Key: <your secret>
# Default region name: us-east-1
# Default output format: json

# Always verify after configuring:
aws sts get-caller-identity
What does aws configure do?

Stores your Access Key ID and Secret in ~/.aws/credentials. Every CLI command after this automatically uses those credentials — you never type them per command. Setting us-east-1 as default region is important because all resources in this project (DynamoDB, Lambda, API Gateway, S3) are hardcoded to us-east-1. Output json makes CLI responses structured JSON, easier to parse with --query and python3 -m json.tool.

What does aws sts get-caller-identity do and why run it?

STS = Security Token Service. This asks AWS "who am I?" and returns your Account ID, IAM User ARN, and User ID. It confirms credentials work before you touch anything. If this fails, nothing else will work. You also need the 12-digit Account ID it returns later when constructing Lambda ARNs manually in Phase 2.

⚠️
IAM permissions required on your AWS user: CloudFormation (full), Lambda (full), API Gateway (full), DynamoDB (full), S3 (full), IAM — create/update roles and policies, CloudWatch Logs — create/write. In an interview environment these are usually pre-granted.

3
Phase 1 — Infrastructure via CloudFormation
Why Phase 1 must run first: CloudFormation creates DynamoDB (Lambda must write somewhere), the IAM role (Lambda must have permissions), API Gateway (Lambda needs a front door), and the S3 bucket (frontend needs a home). None of Phase 2 or Phase 3 is possible without Phase 1. This is a hard dependency chain, not a preference.
🏗️
What CloudFormation actually is: Instead of clicking "Create Table" in DynamoDB, "Create API" in API Gateway, etc. manually, you write one YAML file describing every resource. CloudFormation reads it, figures out the creation order based on dependencies, and creates everything. This is Infrastructure as Code (IaC). Benefit: delete and recreate the entire stack identically with one command. No forgetting a setting, no manual clicking.
1
Deploy the CloudFormation stack
aws cloudformation deploy \
  --template-file infrastructure/infrastructure.yaml \
  --stack-name url-shortener-infra \
  --capabilities CAPABILITY_NAMED_IAM \
  --region us-east-1 \
  --parameter-overrides Environment=dev \
  --no-fail-on-empty-changeset
Flag / ArgumentWhat it does and why it is here
aws cloudformation deployCreates or updates a CloudFormation stack. Internally it creates a "change set" (a diff of what will change), shows you, then executes it. If the stack does not exist yet, it creates everything fresh. If it exists, it updates only what changed — safe to run multiple times.
--template-file infrastructure/infrastructure.yamlPoints to the IaC YAML file relative to your current directory. This file defines every resource: DynamoDB table, API Gateway HTTP API, Lambda IAM role, S3 bucket, S3 bucket policy, and 3 CloudWatch Log Groups. CloudFormation reads it and figures out creation order automatically.
--stack-name url-shortener-infraThe name CloudFormation uses to group all your resources. Think of it as a project folder — all resources created by this template are tagged with this stack name. You reference this same name in every later command to get outputs (API URL, bucket name, etc.). Must be unique in your AWS account + region combination.
--capabilities CAPABILITY_NAMED_IAMAn explicit safety acknowledgement required whenever your template creates IAM resources with hardcoded names. Your template has RoleName: url-shortener-infra-lambda-role — an explicitly named IAM role. AWS forces you to acknowledge this because named IAM resources are harder to track and audit. CAPABILITY_IAM (without NAMED) only covers auto-named IAM resources and will fail here.
--region us-east-1Tells CloudFormation which AWS region to deploy into. All resources will be created in us-east-1 (N. Virginia). The backend Lambda code is also hardcoded to us-east-1 (the DynamoDB client is initialised with region_name='us-east-1'). These must match or Lambda cannot reach DynamoDB.
--parameter-overrides Environment=devPasses a value into the template Parameters section. The template uses this as the API Gateway stage name, which becomes the /dev path segment in your API URL (https://id.execute-api.region.amazonaws.com/dev). If you passed Environment=prod, the stage would be /prod.
--no-fail-on-empty-changesetNormally, if nothing changed in the template and you re-run this command, CloudFormation returns an error saying "no changes." This flag suppresses that error so re-running is always safe — essential in scripts and CI/CD pipelines where you want to guarantee the stack is in sync without checking first.
What happens inside AWS when you run this command?

CloudFormation reads your YAML, builds a dependency graph (e.g. S3 BucketPolicy depends on S3 Bucket, Lambda Role depends on nothing), then creates resources in the right order — parallelising where safe. Each resource shows "CREATE_IN_PROGRESS" then "CREATE_COMPLETE". The whole stack takes 2–3 minutes. Resources created: LinksTable (DynamoDB), HttpApi (API Gateway v2), ApiStage (/dev stage), LambdaExecutionRole (IAM), FrontendBucket (S3), FrontendBucketPolicy (public read), and 3 CloudWatch Log Groups.

🔴
Issue hit during deployment: InsufficientCapabilitiesException 
An error occurred (InsufficientCapabilitiesException) when calling the
CreateChangeSet operation: Requires capabilities : [CAPABILITY_NAMED_IAM]
Why it happened: The original command used --capabilities CAPABILITY_IAM. But the template has RoleName: !Sub "${AWS::StackName}-lambda-role" — an IAM role with an explicit custom name. AWS requires the stricter CAPABILITY_NAMED_IAM for any template that names IAM resources explicitly.

Fix: Replace CAPABILITY_IAM with CAPABILITY_NAMED_IAM (already corrected in the command above).

Rule to remember: CAPABILITY_IAM = unnamed/auto-named IAM resources OK. CAPABILITY_NAMED_IAM = explicitly-named IAM resources OK (superset — covers both cases). When in doubt, always use CAPABILITY_NAMED_IAM. It will never fail where CAPABILITY_IAM would succeed.
Why is this Step 1 of the entire deployment?

Because every other step in this guide depends on what this command creates. Lambda create-function needs the IAM role ARN (created here). API Gateway route creation needs the API ID (created here). S3 sync needs the bucket name (created here). Lambda needs a DynamoDB table to write to (created here). This is the foundation — skip or fail this and nothing else in the guide is possible.

2
Get and save the stack outputs
aws cloudformation describe-stacks \
  --stack-name url-shortener-infra \
  --query 'Stacks[0].Outputs[*].[OutputKey,OutputValue]' \
  --output table
Flag / ArgumentWhat it does and why
describe-stacksFetches the current state of a named CloudFormation stack — its status, parameters, and importantly its Outputs. Outputs are values the template explicitly exports (API URL, bucket name, etc.) that you need to use in subsequent steps. Without this command you would have to hunt through the AWS console to find each value.
--stack-name url-shortener-infraMust exactly match the name used in the deploy command. This identifies which stack's data to return.
--query 'Stacks[0].Outputs[*].[OutputKey,OutputValue]'JMESPath query that filters the large JSON response. Stacks[0] = first result (only one stack with this name). Outputs[*] = all outputs. .[OutputKey,OutputValue] = return only the name and value columns, dropping extra metadata. Without this, the full response is hard to read.
--output tableFormats the filtered result as a human-readable ASCII table. Much easier to scan than raw JSON, especially when you are looking for specific values to copy into other commands.
What outputs you will see and why you need each one

ApiGatewayUrl — e.g. https://abc123.execute-api.us-east-1.amazonaws.com/dev. This goes into app.js and admin.js in Phase 3. Without it the frontend will not talk to your backend.

ApiGatewayId — e.g. abc123. Needed in Phase 2 to create integrations and routes, and to grant Lambda permissions.

DynamoDBTableName — the actual table name (url-shortener-infra-links). Your Lambda functions have this hardcoded — verify they match exactly.

LambdaRoleArn — the full ARN of the IAM role. You supply this when creating each Lambda function.

S3BucketName — the actual bucket name with account ID suffix. Needed in Phase 3 for the sync command.

S3WebsiteUrl — the public HTTP URL of your frontend. This is what you open in the browser.

Why collect outputs immediately after Phase 1?

Every step in Phase 2 and Phase 3 requires values that only exist after Phase 1. Collecting them now in one command means you have everything at hand before starting Phase 2 — no stopping mid-deployment to look things up. In a timed interview, this saves valuable minutes.

aws dynamodb list-tables --region us-east-1

# Verify S3 bucket
aws s3 ls | grep url-shortener

# Verify API Gateway
aws apigatewayv2 get-apis --region us-east-1
Why verify manually instead of trusting CloudFormation said "CREATE_COMPLETE"?

CloudFormation reports completion for the stack as a whole, but occasionally resources have subtle issues — wrong billing mode, wrong region, missing policy. Verifying takes 30 seconds and catches issues before you build on top of them. If you skip this and something is wrong, you will get confusing errors deep in Phase 2 and waste time debugging the wrong layer.

aws dynamodb list-tables — confirms the exact table name. Lambda hardcodes url-shortener-infra-links. If CloudFormation named it differently (e.g. because of a stack name mismatch), every Lambda DynamoDB call fails with ResourceNotFoundException.

aws apigatewayv2 get-apis — note the v2 here. This project uses API Gateway HTTP API (v2), not REST API (v1). They are different services with different CLI commands. If you run aws apigateway get-rest-apis (v1) you will see nothing — use apigatewayv2.

4
Phase 2 — Backend: Deploy 3 Lambda Functions
Why Phase 2 runs second: Lambda functions need the IAM role from Phase 1 to be created with. They need to be attached to the API Gateway from Phase 1 via integrations and routes. You also need the DynamoDB table name from Phase 1 to pass as an environment variable. None of this is possible before Phase 1. Phase 2 runs before Phase 3 because the frontend needs a working API URL — which only makes sense once Lambda functions are wired up.
⚡
What deploying a Lambda function means: Lambda does not run on a server that is always on. You upload a ZIP file containing your Python code to AWS. AWS stores it. When an API Gateway request arrives, AWS spins up a micro-container, runs your handler function, returns the response, then shuts down. The ZIP is your deployment package. No provisioning, no SSH, no server management.
1
Create the deployment ZIP packages
mkdir -p build

cd src/backend/functions && zip ../../../build/create_link.zip create_link.py && cd ../../..
cd src/backend/functions && zip ../../../build/redirect_link.zip redirect_link.py && cd ../../..
cd src/backend/functions && zip ../../../build/admin_links.zip admin_links.py && cd ../../..
PartWhat it does and why
mkdir -p buildCreates a /build directory at the project root for the ZIP files. The -p flag means "create parent directories if needed, and do not error if already exists." Done first because the zip command will fail if the destination directory does not exist.
cd src/backend/functionsNavigates into the folder containing the .py files before zipping. This is critical: when zip runs, the file is added to the archive relative to the current directory. If you zip from elsewhere, the file ends up inside a subfolder in the ZIP, and Lambda will fail to find the handler file at runtime because it looks for it at the root of the ZIP.
zip ../../../build/create_link.zip create_link.pyCreates the ZIP archive. ../../../build/ navigates three levels up (functions → backend → src → project root) then into build/. The result is a ZIP where create_link.py sits at the root — exactly how Lambda requires it.
cd ../../..Navigates back to the project root after each zip so the next cd command starts from the correct location. Forget this and the paths cascade incorrectly.
Why ZIP? Why not just point Lambda at the .py file directly?

Lambda does not have access to your local filesystem or GitHub. The only way to get code into Lambda is to package it as a ZIP and upload it. AWS stores the ZIP, extracts it into a temporary execution environment, and calls your handler when a request arrives. If your function needed external packages like requests, you would also run pip install requests -t . inside the functions folder to bundle them into the ZIP. This project only uses boto3 which is pre-installed in all Lambda Python runtimes — so the .py file alone is sufficient.

Why create all three ZIPs before creating any Lambda function?

The aws lambda create-function command requires you to supply the ZIP at creation time. Creating all ZIPs first means you can run all three create-function commands back-to-back without switching tasks. It also makes it easy to spot if a ZIP is missing before wasting time on the create-function calls.

2
Get the Lambda IAM Role ARN
ROLE_ARN=$(aws cloudformation describe-stacks \
  --stack-name url-shortener-infra \
  --query "Stacks[0].Outputs[?OutputKey=='LambdaRoleArn'].OutputValue" \
  --output text)

echo "Role ARN: $ROLE_ARN"
# Should print: arn:aws:iam::264449293739:role/url-shortener-infra-lambda-role
What is an IAM Role and why does Lambda need one?

An IAM Role is a set of permissions that an AWS service can assume. Your Lambda function needs two things: (1) permission to write logs to CloudWatch so you can debug it, and (2) permission to read and write records in DynamoDB. Without a role granting these, Lambda gets AccessDeniedException on every DynamoDB call. The role was created in Phase 1 with exactly these policies. You are fetching its ARN (Amazon Resource Name — a globally unique identifier for any AWS resource) to assign it to your functions.

Command breakdown — the shell substitution and query syntax

$(...) = shell command substitution. Runs the inner command and stores its printed output in the ROLE_ARN variable. Every subsequent reference to $ROLE_ARN uses this stored value.

Stacks[0].Outputs[?OutputKey=='LambdaRoleArn'].OutputValue = JMESPath filter. From the Outputs array, find the item where OutputKey equals 'LambdaRoleArn', then return only its OutputValue. --output text returns it as plain text without JSON quotes so it stores cleanly in a shell variable.

Why fetch this dynamically instead of hardcoding the ARN?

The ARN contains your AWS account ID (12-digit number) and the stack name — both of which differ per person and per environment. Fetching it dynamically means this guide works for any AWS account without edits. Hardcoding would break for anyone using a different account or stack name.

aws lambda create-function \

  --zip-file fileb://build/redirect_link.zip \
  --region us-east-1 \

# 3. Admin Links Function
aws lambda create-function \
  --function-name url-shortener-infra-adminLinks \
  --runtime python3.9 \
  --role $ROLE_ARN \

  --region us-east-1 \

FlagWhat it does and why set this way
--function-nameThe name of the Lambda function in AWS. Must be unique within a region. Prefixed with the stack name (url-shortener-infra-) to group related functions and avoid collisions with other projects in the same account. The deploy-backend.py script searches for functions matching this prefix pattern.
--runtime python3.9Tells Lambda which language environment to execute your code in. Must match what your code was written for. Python 3.9 is the version specified in package.json and is stable with good boto3 support. Lambda has boto3 pre-installed for all Python runtimes so you do not need to bundle it in the ZIP.
--role $ROLE_ARNAssigns the IAM role fetched in Step 2. This is what gives the function permission to access DynamoDB and write to CloudWatch Logs. Without this, every DynamoDB call returns AccessDeniedException and you would see nothing in CloudWatch either.
--handler create_link.lambda_handlerTells Lambda exactly which function to call when triggered. Format: filename.function_name. create_link = the Python file (create_link.py, without the .py extension). lambda_handler = the function defined as def lambda_handler(event, context) inside that file. This is the standard Lambda entry point convention — all three files follow it.
--zip-file fileb://build/create_link.zipThe deployment package path. fileb:// prefix means "file, binary mode" — required for binary files like ZIPs (as opposed to text files which use file://). Relative to your current working directory — another reason you must run commands from the project root.
--environment Variables={TABLE_NAME=...}Sets environment variables inside the Lambda execution environment. Your Python code reads the table name with os.environ.get('TABLE_NAME') rather than hardcoding it. This means you can deploy to a staging environment with a different table just by changing the env var — no code changes needed.
For re-deployments — use update-function-code instead

create-function fails if the function already exists (it is not idempotent — cannot be run twice safely). update-function-code replaces the code ZIP without touching configuration (role, timeout, env vars). Use this on every re-deploy after the first:

aws lambda update-function-code \
  --function-name url-shortener-infra-createLink \
  --zip-file fileb://build/create_link.zip \
  --region us-east-1
# Repeat for redirectLink and adminLinks
4
Wire Lambda functions to API Gateway routes
# Get API Gateway ID and build Lambda ARNs
API_ID=$(aws cloudformation describe-stacks \
  --stack-name url-shortener-infra \
  --query "Stacks[0].Outputs[?OutputKey=='ApiGatewayId'].OutputValue" \
  --output text)

ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
REGION=us-east-1
CREATE_ARN="arn:aws:lambda:$REGION:$ACCOUNT_ID:function:url-shortener-infra-createLink"
REDIRECT_ARN="arn:aws:lambda:$REGION:$ACCOUNT_ID:function:url-shortener-infra-redirectLink"
ADMIN_ARN="arn:aws:lambda:$REGION:$ACCOUNT_ID:function:url-shortener-infra-adminLinks"

# Create integrations (the connection objects between API GW and Lambda)
CREATE_INTEG=$(aws apigatewayv2 create-integration \
  --api-id $API_ID --integration-type AWS_PROXY \
  --integration-uri $CREATE_ARN --payload-format-version 2.0 \
  --query IntegrationId --output text)

REDIRECT_INTEG=$(aws apigatewayv2 create-integration \
  --api-id $API_ID --integration-type AWS_PROXY \
  --integration-uri $REDIRECT_ARN --payload-format-version 2.0 \
  --query IntegrationId --output text)

ADMIN_INTEG=$(aws apigatewayv2 create-integration \
  --api-id $API_ID --integration-type AWS_PROXY \
  --integration-uri $ADMIN_ARN --payload-format-version 2.0 \
  --query IntegrationId --output text)

# Create the actual HTTP routes pointing to each integration
aws apigatewayv2 create-route --api-id $API_ID \
  --route-key "POST /links" --target integrations/$CREATE_INTEG

aws apigatewayv2 create-route --api-id $API_ID \
  --route-key "GET /{code}" --target integrations/$REDIRECT_INTEG

aws apigatewayv2 create-route --api-id $API_ID \
  --route-key "GET /admin/links" --target integrations/$ADMIN_INTEG
Why is wiring routes a separate step from creating Lambda functions?

API Gateway and Lambda are two completely separate AWS services. Creating a Lambda function does NOT automatically make it reachable via HTTP. You need to explicitly tell API Gateway: "when you receive a POST /links request, forward it to this Lambda." That connection is called an integration. Think of it like this: Lambda = a phone. Creating Lambda = buying the phone. Creating an integration and route = assigning that phone a public number and advertising it.

🔴
⚠️ Critical lesson learned in testing: Do NOT use this manual wiring approach with a CloudFormation-managed API Gateway

Manually creating integrations and routes on an API Gateway that was created by CloudFormation causes a fundamental conflict. The CloudFormation-managed stage tracks a "deployment snapshot" of routes at the time it was deployed. Routes added manually afterwards are NOT included in that snapshot — so the stage ignores them and continues serving the old deployment (which has no routes). The result is persistent 500 errors where Lambda is never invoked, even though the routes visually appear correct when you run get-routes.

The correct approach for this project: Lambda functions, integrations, and routes must ALL be defined inside infrastructure.yaml so CloudFormation manages them together and deploys them atomically. Do not create any of these manually as a separate step. When everything is in the YAML, CloudFormation creates them with correct deployment tracking from the start.

If you already created resources manually and need to fix it: 
# 1. Delete manually created routes (integrations cannot be deleted while routes reference them)
aws apigatewayv2 delete-route --api-id $API_ID --route-id <route-id> --region $REGION

# 2. Delete manually created integrations
aws apigatewayv2 delete-integration --api-id $API_ID --integration-id <integ-id> --region $REGION

# 3. Delete manually created Lambda functions
aws lambda delete-function --function-name url-shortener-infra-createLink --region us-east-1
aws lambda delete-function --function-name url-shortener-infra-redirectLink --region us-east-1
aws lambda delete-function --function-name url-shortener-infra-adminLinks --region us-east-1

# 4. Add Lambda + integrations + routes to infrastructure.yaml, then redeploy:
aws cloudformation deploy \
  --template-file infrastructure/infrastructure.yaml \
  --stack-name url-shortener-infra \
  --capabilities CAPABILITY_NAMED_IAM \
  --region us-east-1 --parameter-overrides Environment=dev

# 5. After stack deploys, upload real code (CloudFormation uses placeholder):
aws lambda update-function-code --function-name url-shortener-infra-createLink \
  --zip-file fileb://build/create_link.zip --region us-east-1
aws lambda update-function-code --function-name url-shortener-infra-redirectLink \
  --zip-file fileb://build/redirect_link.zip --region us-east-1
aws lambda update-function-code --function-name url-shortener-infra-adminLinks \
  --zip-file fileb://build/admin_links.zip --region us-east-1
ConceptExplanation
create-integrationCreates a connection object between API Gateway and a Lambda. AWS_PROXY type means API Gateway passes the full HTTP request (headers, body, path params, method) directly to Lambda as a JSON event object, and Lambda returns the full HTTP response including status code and headers. Lambda handles everything — this is the standard pattern.
--payload-format-version 2.0Specifies the format of the event object Lambda receives. Version 2.0 is simpler and newer. Your Lambda code uses the v2.0 structure (it checks event.get('requestContext', {}).get('http', {}).get('method')). Using 1.0 would break the CORS handling logic in all three functions because the event structure is different.
--route-key "GET /{code}"The HTTP method + path pattern that triggers this route. Curly braces denote a path parameter — {code} captures whatever comes after the slash and passes it as pathParameters.code in the Lambda event. This is how redirect_link.py gets the short code from the URL.
--target integrations/$INTEG_IDLinks the route to the integration just created. The "integrations/" prefix is required — it is how API Gateway distinguishes integration targets from other target types. The integration ID was captured in the variable by storing the create-integration output.
5
Grant API Gateway permission to invoke Lambda
aws lambda add-permission \
  --function-name url-shortener-infra-createLink \
  --statement-id apigw-create \
  --action lambda:InvokeFunction \
  --principal apigateway.amazonaws.com \
  --source-arn "arn:aws:execute-api:$REGION:$ACCOUNT_ID:$API_ID/*/*"

# Repeat for redirectLink with --statement-id apigw-redirect
# Repeat for adminLinks with  --statement-id apigw-admin
Why is this a separate step? Did creating the integration not wire things up?

This is a common point of confusion. Creating the integration (Step 4) tells API Gateway which Lambda to call. But Lambda has its own separate resource-based permission system — a policy attached to the function itself — that controls who is allowed to invoke it. By default, nothing is allowed to invoke Lambda, not even API Gateway. You must explicitly grant the permission here. This is AWS defense-in-depth security: two separate checks must both pass. API Gateway must be allowed to invoke Lambda (this step) AND Lambda must have an IAM role to call DynamoDB (Phase 1). Two separate permission layers.

FlagWhat it does
--statement-id apigw-createA unique label for this permission entry in the Lambda resource policy. Must be unique per function. If you run this command twice with the same statement-id it fails with "already exists" — use a different ID or delete the existing permission first.
--action lambda:InvokeFunctionThe specific IAM action being granted — the ability to execute the function. Minimum permission needed for API Gateway to trigger Lambda.
--principal apigateway.amazonaws.comWho is being granted permission — the API Gateway service itself, identified by its service principal. This is not a user or role — it is AWS's own service identity.
--source-arn "arn:aws:execute-api:..."Scopes the permission so ONLY your specific API Gateway (identified by $API_ID) can invoke this Lambda. The /* /* at the end means any stage, any method. Without this, any API Gateway in your entire account could invoke this function — a security risk.

Phase 3 — Frontend: Deploy to S3
Why Phase 3 runs last: The JavaScript files must contain your real API Gateway URL before being uploaded. That URL only exists after Phase 1 (API Gateway created) and is only meaningful after Phase 2 (Lambda functions wired up and responding to requests). Deploying frontend first would mean serving a broken app that points nowhere.
🌐
How S3 static hosting works: S3 is normally cloud file storage. In "static website" mode it acts as a web server — serving HTML/CSS/JS directly to browsers over HTTP. No Node.js process, no nginx, no server to manage. Files are stored as S3 objects and served at a public URL. Scales to millions of requests automatically. Extremely cheap — you pay for storage and data transfer only.
1
Update the API URL in frontend JS files
# First get your real API URL
API_URL=$(aws cloudformation describe-stacks \
  --stack-name url-shortener-infra \
  --query "Stacks[0].Outputs[?OutputKey=='ApiGatewayUrl'].OutputValue" \
  --output text)
echo "Your API URL: $API_URL"

Now open src/frontend/assets/app.js AND src/frontend/assets/admin.js and update the CONFIG at the top of each:

const CONFIG = {
    API_BASE_URL: 'https://<YOUR_API_ID>.execute-api.us-east-1.amazonaws.com/dev',
    DEMO_MODE: false,    // ← must be false for production
    AUTO_FALLBACK: true
};
Why must you update this before uploading to S3?

The frontend JavaScript runs entirely in the user's browser — it is not server-side code. When a user clicks "Shorten URL", their browser directly calls the API_BASE_URL via JavaScript fetch(). If this URL is wrong, the app detects the failure and silently falls back to DEMO_MODE — showing fake locally-generated data with no real backend interaction. Your links would not actually be stored anywhere.

You must update both app.js (used by index.html for the shortener) and admin.js (used by admin.html for the dashboard) — they each have their own CONFIG object at the top.

Setting DEMO_MODE: false forces the app to call the real API instead of generating mock data locally.

Why edit files locally before uploading rather than after?

S3 serves static files — there is no way to inject runtime variables or run code on S3. The API URL must be baked into the JS file before it is uploaded. This is the standard pattern for static web apps. Modern frameworks like React and Vue use build-time environment variables (process.env.REACT_APP_API_URL) for exactly the same reason — the URL gets embedded into the built bundle before deployment.

aws logs describe-log-streams \

Issue 2 Hit: Malformed Lambda ARN in IntegrationUri — :function: missing 
# Broken (what was found):
"IntegrationUri": "arn:aws:lambda:us-east-1:690081480550nction:url-shortener-infra-createLink"

# Correct (what it should be):
"IntegrationUri": "arn:aws:lambda:us-east-1:690081480550:function:url-shortener-infra-createLink"
Why it happened: When constructing the ARN string manually in the terminal, if the variable $ACCOUNT_ID is not set or has a trailing character issue, the shell concatenates it directly into :function: and the :f prefix gets absorbed. The ARN looks almost right but is invalid — API Gateway silently returns 500 rather than a clear "bad ARN" error.

Fix — delete routes first (routes block integration deletion), then delete integrations, then recreate with correct ARNs:

# Must delete routes first:
aws apigatewayv2 delete-route --api-id $API_ID --route-id <route-id> --region $REGION
# Repeat for all 3 routes

# Then delete the broken integrations:
aws apigatewayv2 delete-integration --api-id $API_ID --integration-id <integ-id> --region $REGION
# Repeat for all 3 integrations

# Then build ARNs correctly — verify $ACCOUNT_ID is set first:
echo $ACCOUNT_ID  # Must print a 12-digit number, e.g. 690081480550
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)  # Re-set if empty

CREATE_ARN="arn:aws:lambda:$REGION:$ACCOUNT_ID:function:url-shortener-infra-createLink"

Issue 3 Hit: Manually created routes not picked up by CloudFormation-managed API Gateway stage

After fixing the ARNs and recreating integrations/routes manually, API Gateway still returned 500 and CloudWatch logs remained empty. The routes were correctly wired and the Lambda permissions were correct — but the stage was not serving the manually added routes.

Root cause: When a CloudFormation-managed API Gateway stage has AutoDeploy enabled, it creates a "deployment" that is a snapshot of the API's routes at the time CloudFormation deployed it. Routes added manually afterwards are not automatically included in that deployment snapshot. The stage was still serving the old deployment (which had no routes at all) rather than the current state of the API.

Why this is a fundamental design conflict: CloudFormation owns this API stage. Manually adding routes alongside CloudFormation-managed resources creates a state mismatch. CloudFormation thinks the API has no routes; reality has routes; the stage deployment reflects CloudFormation's view.

The correct fix — move Lambda functions, integrations, and routes INTO infrastructure.yaml so CloudFormation owns everything: 
# This is the key architectural lesson:
# Resources created manually OUTSIDE CloudFormation are invisible to CloudFormation's
# deployment tracking. Add Lambda functions, integrations, and routes to the YAML template
# so everything is managed together and deployed atomically.

# After updating infrastructure.yaml, delete the manually created Lambda functions
# (CloudFormation cannot adopt externally created resources with same names):
aws lambda delete-function --function-name url-shortener-infra-createLink --region us-east-1
aws lambda delete-function --function-name url-shortener-infra-redirectLink --region us-east-1
aws lambda delete-function --function-name url-shortener-infra-adminLinks --region us-east-1

# Delete manually created routes and integrations too (they conflict):
aws apigatewayv2 delete-route --api-id $API_ID --route-id <id> --region $REGION
aws apigatewayv2 delete-integration --api-id $API_ID --integration-id <id> --region $REGION

# Then redeploy CloudFormation — it creates everything cleanly:
aws cloudformation deploy \
  --template-file infrastructure/infrastructure.yaml \
  --stack-name url-shortener-infra \
  --capabilities CAPABILITY_NAMED_IAM \
  --region us-east-1 \
  --parameter-overrides Environment=dev \
  --no-fail-on-empty-changeset

# After stack deploys, upload your actual code (CloudFormation uses placeholder code):
cd src/backend/functions

zip ../../../build/redirect_link.zip redirect_link.py

  --zip-file fileb://build/admin_links.zip --region us-east-1
Key rule to remember: Never mix manually created AWS resources with CloudFormation-managed resources in the same stack. Either manage everything through CloudFormation, or manage everything manually. Mixing them causes deployment tracking conflicts exactly like this.

Key design decisions to explain in an interview

Why DynamoDB not PostgreSQL? URL shorteners have one access pattern: look up by short code. DynamoDB primary key lookup is O(1) with single-digit millisecond latency — perfect for redirect performance. SQL is overkill, no joins needed, no complex queries needed.

Why on-demand billing? URL shorteners have highly variable traffic. On-demand means pay per request with automatic scaling. Provisioned mode requires predicting traffic upfront and over-provisioning.

Why ADD not SET for click_count? DynamoDB's atomic ADD is thread-safe. Two simultaneous redirects both calling ADD :1 will both succeed and count correctly. Two simultaneous redirects using SET (read-then-write) would both read "5", both write "6", and you would lose a count.

Why String for created_at not a date type? DynamoDB has no native datetime type. ISO 8601 strings sort lexicographically in the same order as chronologically — so date-range queries still work correctly even as plain strings.

create_link.py — What it does step by step
# 1. Parse JSON body from event['body']
# 2. Validate URL with urlparse — must have http or https scheme and a netloc (domain)
# 3. Check URL length is at most 2048 characters
# 4. If customCode: validate with regex ^[a-zA-Z0-9]{3,50}$ (3-50 alphanumeric chars)
# 5. If no customCode: generate random 6-char Base62 string (a-z A-Z 0-9 = 62^6 options)
#    Check for collision in DynamoDB, retry up to 5 times if collision
# 6. DynamoDB put_item with ConditionExpression='attribute_not_exists(code)'
#    If condition fails because code exists: return 409 Conflict
# 7. Return 201 with shortCode, shortUrl, targetUrl, createdAt
Key points to remember

ConditionExpression='attribute_not_exists(code)' makes the write atomic. It says "only write this item if no item with this code already exists." Without this, two near-simultaneous requests generating the same random code could both succeed and one would silently overwrite the other. The condition check and write happen atomically in DynamoDB.

Base62 with 6 characters: 62^6 = about 56 billion possible codes. The probability of a collision on any single generation is 1 in 56 billion. The retry loop handles this astronomically rare case anyway.

📄
redirect_link.py — What it does step by step
# 1. Extract short code from event['pathParameters']['code']
# 2. DynamoDB get_item(Key={'code': short_code})
# 3. If not found: return 404 HTML error page with user-friendly message
# 4. table.update_item: ADD click_count :1 (atomic thread-safe increment)
#    Fire-and-forget: the 301 redirect is returned whether or not this update succeeds
# 5. Return 301 with Location: target_url and Cache-Control: no-cache
Interesting nuance — 301 vs 302 and Cache-Control

301 = Permanent Redirect (browsers cache it). 302 = Temporary Redirect (not cached). 301 would mean after the first visit, the browser redirects directly without hitting the server — faster but means if you change the target URL in DynamoDB, cached users still go to the old destination. Adding Cache-Control: no-cache with a 301 actually disables the caching, making it behave like a 302 in practice. Worth flagging in an interview as a nuance.

📄
admin_links.py — What it does step by step
# 1. Read query params: limit (default 50), lastKey (pagination cursor)
# 2. DynamoDB table.scan() — reads ALL items (no key filter)
#    Uses Limit and ExclusiveStartKey for pagination
# 3. convert_decimals(): DynamoDB returns numbers as Python Decimal type
#    json.dumps() cannot serialize Decimal — must convert to int or float first
# 4. Calculate statistics from the result set:
#    totalClicks = sum of all click_counts
#    averageClicks = totalClicks / len(links)
#    todayLinks = count of links where created_at starts with today's ISO date
# 5. Return links array + pagination + statistics
Why scan() and not query()?

DynamoDB query() requires a partition key value — it fetches items with a known key. scan() reads the entire table regardless of key. For the admin dashboard where you want ALL links with no filter, scan() is correct. The trade-off is scan() reads every item and costs more for large tables. For a URL shortener at typical scale this is fine. At millions of records you would add a secondary index (GSI) to enable more efficient filtered queries.

Talking Points for Interviewers

Why Serverless / Lambda?

No servers to provision or manage. Auto-scales from 0 to millions. Pay per invocation — free tier covers early traffic. Cold starts (~200ms) are the only trade-off, acceptable here since redirect traffic keeps functions warm.

Why DynamoDB over RDS?

URL shorteners have one access pattern: look up by code. DynamoDB primary key lookup is O(1), single-digit milliseconds. No joins needed. On-demand billing handles variable traffic perfectly. SQL would be overkill.

Why API Gateway HTTP API not REST API?

HTTP APIs are about 71% cheaper and lower latency. We only need basic routing and CORS — no usage plans, API keys, or request transformation that REST API provides.

Why CloudFormation over manual setup?

Infrastructure as Code means reproducible, version-controlled, one-command deploy and teardown. No snowflake environments. Dev, staging, and production are guaranteed identical.

How does collision avoidance work?

Random 6-char Base62 = 56 billion possibilities. DynamoDB conditional write with attribute_not_exists makes it atomic. Up to 5 retries. Astronomically unlikely to need them at normal scale.

How does click tracking work?

DynamoDB atomic ADD — thread-safe, no lost counts under concurrent load. Fire-and-forget: redirect returns before the update completes so user latency is not affected.

Security considerations

IAM least-privilege roles. URL validation via urlparse. Custom code regex. Conditional DynamoDB writes prevent overwrites. CORS configured. No secrets in code — env vars for table names.

What would you add next?

Custom domain via Route 53 and CloudFront for HTTPS. Link expiry using DynamoDB TTL attribute. API key authentication. Rate limiting per user. DELETE endpoint. Bulk link creation via CSV upload.
